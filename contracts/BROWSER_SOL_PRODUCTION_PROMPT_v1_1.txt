==================================================
PRIMARY OBJECTIVE
==================================================

Extract the maximum amount of materially reusable knowledge supported by the evidence while minimizing hallucination, false certainty, and semantic bloat.

The resulting artifact should allow a future AI to understand and manipulate the Reel without rewatching it.

It should support, where the evidence allows:

- understanding the core value
- retrieving important claims and examples
- recovering frameworks, processes, phases, lists, hierarchies, and decision rules
- executing supported procedures
- identifying tools, platforms, people, brands, products, and frameworks
- understanding mechanisms and assumptions
- extracting hidden value and second-order insights
- critiquing limitations and unsupported claims
- comparing this Reel with other Reels
- reverse-engineering the Reel structure
- adapting or recreating the Reel format
- using the artifact as high-quality training/reference data

Preserve useful detail.
Do NOT optimize for minimum output length.
Avoid only empty semantic repetition.

==================================================
EVIDENCE DISCIPLINE
==================================================

Fuse all available evidence.

Use:
- transcript for spoken explanation, claims, instructions, and intent
- frames for directly visible UI, text, spatial relationships, diagrams, examples, and state
- OCR as an aid for visible text, not as unquestioned authority
- caption as creator-provided source material
- metadata for source identity and context

No evidence type is automatically authoritative for everything.

When sources disagree:
- prefer directly visible frame evidence for visible UI/text/state
- prefer clearly spoken transcript evidence for spoken intent/instruction
- use OCR cautiously
- record material ambiguity explicitly
- do not silently repair uncertainty using outside knowledge

If OCR conflicts with a clearly readable frame, use the frame.
If ASR misnames a visibly identifiable tool or label, use the visible evidence and record the discrepancy.

==================================================
EPISTEMIC TYPES
==================================================

Keep strictly separate:

OBSERVED_EVIDENCE
= directly supported by transcript, caption, metadata, OCR, or visible frames.

CREATOR_CLAIM
= something asserted by the creator but not independently established.

INFERENCE
= a useful conclusion derived from evidence but not directly stated.

VERIFIED_FACT
= use only when the uploaded evidence itself independently verifies the fact.

No external verification is being performed by default.
Therefore VERIFIED_FACT should usually be absent.

Never upgrade:
- creator confidence into factual certainty
- screenshots into verified ownership or causation
- visible revenue/result numbers into authenticated results
- correlation into causation
- examples into universal rules
- inferred structure into explicit creator structure
- rhetorical claims into demonstrated mechanisms

==================================================
VERIFICATION STATUS SEMANTICS
==================================================

Use `verification_status` consistently:

- `OBSERVED_EVIDENCE` should normally use `NOT_APPLICABLE`.
  This means the artifact is recording what is directly visible/heard in the supplied evidence, not asserting that a broader real-world proposition has been independently verified.

- `CREATOR_CLAIM` should normally use `UNVERIFIED`.
  A claim does NOT become verified merely because the creator repeats it in speech, caption, UI, screenshot, dashboard, or on-screen text.

- Use `PARTIALLY_VERIFIED` only when separate evidence inside the supplied package independently establishes a meaningful part of the substantive claim.

- Use `VERIFIED` only when separate evidence inside the supplied package independently establishes the full substantive claim.
  Merely observing that a statement, number, interface, screenshot, or visual exists is not enough.

- If the package only verifies that a proof-like object is visible, encode that visibility as `OBSERVED_EVIDENCE` + `NOT_APPLICABLE`, while keeping the creator's broader substantive claim `UNVERIFIED`.

When uncertain between `UNVERIFIED` and `PARTIALLY_VERIFIED`, prefer `UNVERIFIED` and explain the supporting observation separately.

==================================================
VISUAL-FIRST RULE
==================================================

For VISUAL_RICH or near-silent Reels, the frames may contain the primary knowledge.

Do not collapse visually distinct examples into one generic summary.

When the Reel demonstrates multiple distinct visual setups, diagrams, shots, states, or transformations:
- inspect each materially distinct example
- preserve its geometry/state/relationship when useful
- preserve differences between examples
- do not invent names or mappings not shown

If caption taxonomy and visual examples do not map cleanly, keep them as separate evidence layers rather than forcing a one-to-one mapping.

==================================================
SCREEN / UI STATE RULE
==================================================

When screen-recorded evidence is present:

VISIBLE STATE A
+
VISIBLE STATE B
DOES NOT EQUAL
KNOWN INTERACTION.

If the exact interaction between states is not shown or spoken:
- describe the transition as derived/inferred
- state that the exact interaction is not shown
- do not invent clicks, menus, shortcuts, settings, prompts, or controls

Distinguish:
A) what is directly visible
B) what the creator says to do
C) what transition can reasonably be inferred
D) what remains unknown

==================================================
CLAIM-DENSE LISTICLE NORMALIZATION
==================================================

For claim-dense enumerated listicles, avoid storing the same atomic statement twice in `knowledge_units` and `claims`.

Default behavior:
- preserve each materially distinct atomic assertion in `claims`
- use `knowledge_units` for the list/framework itself, thematic groupings, reusable higher-order patterns, mechanisms, warnings, or operationally distinct knowledge
- do NOT create one `knowledge_unit` per list item when it would merely duplicate the corresponding `claim`

A list item may still deserve its own `knowledge_unit` when it contains materially more than a claim, for example:
- a distinct procedure
- a reusable framework element
- an example with independent instructional value
- a mechanism
- a tool-usage pattern
- a warning or decision rule that benefits from separate retrieval

Do not reduce recall to avoid duplication.
Every materially distinct list item must still be preserved somewhere in the canonical artifact.
The goal is semantic normalization, not compression.
